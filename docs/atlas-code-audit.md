# Atlas 公开方法与代码审查

本文是旧 RGBD 输出基线的历史审查；当前 RGB-only 任务与修正见 [模型说明](rgb-next-frame.md)。

审查日期：2026-10-20。代码快照：`8cd12dcc09ee50f6eb92808760c4e2918812551b`。

当前实现是 **RGB／相机条件的逐帧 RGBD rectified-flow 基线**。它具有相机射线条件、逐帧自回归和深度输出，但与 Atlas 公开架构及任务范围存在实质差别，不能作为完整 Atlas 的架构复现。

依据包括 [Atlas 官方技术文章](https://www.worldlabs.ai/blog/atlas)、[DiT 论文](https://arxiv.org/abs/2212.09748)与[官方实现](https://github.com/facebookresearch/DiT/blob/main/models.py)、[CameraCtrl 论文](https://arxiv.org/abs/2404.02101)与[官方相机代码](https://github.com/hehao13/CameraCtrl/blob/af45a7a0dbeedb7f6ed66aac4a9e5411a279f0d2/cameractrl/data/dataset.py)、[CAT3D 本地原文](papers/cat3d-2405.10314.pdf)第 3.1 节、[Diffusion Forcing 论文](https://arxiv.org/abs/2407.01392)及 [Rectified Flow 论文](https://arxiv.org/abs/2209.03003)。Atlas 没有公开足以逐层核对的训练实现；以下区分公开事实、代码事实与设计风险。

## 直接回答

| 能力 | 代码现状 | 依据 |
| --- | --- | --- |
| 根据目标相机轨迹生成图像 | 支持条件输入；控制精度仍需测量 | `sample.py:63` 从 JSON 读取 `c2w` 并构造射线 |
| 预测相机轨迹或从视频估计位姿 | 不支持 | 无位姿输出头、位姿损失或位姿估计流程；`geometry.py:41` 的轨迹是解析函数 |
| 输出生成视图的深度图 | 支持 | `model.py:36` 输出四通道；`sample.py:73` 解码第 4 通道，保存 float32 NPY |
| 固定已有视频 RGB，只估计各帧深度 | 缺少该任务 | 参考帧无深度输出，目标 RGB 不作为观测条件，详见 F1 |
| 使用时只提供 RGB，不提供真值深度 | 支持，但仍须提供相机内外参 | `load_rgb` 与推理路径不加载深度 |
| 深度是否为米制 | 不是 | `mesh.py:19` 将完整网格最长边归一化为 4；输出沿用该坐标尺度 |

Atlas 的相机控制示例也是给定目标路径，不要求模型自行预测拍摄路径。输入视频的位姿估计、目标路径规划、给定路径下的图像生成，是三个不同问题。不能把“没有轨迹预测头”单独判为相机控制任务的实现错误。

## F1：高影响功能缺口——没有输入视频深度重建任务

位置：`open_atlas/sample.py:44`、`:58`、`:62`、`:73`，`open_atlas/data.py:78`。

`generate` 只读取开头 `reference_frames` 张真实 RGB；后续条目仅取相机，生成新的 RGB 和对应深度。参考 RGB 本身没有预测深度输出。即便 JSON 给出整段真实视频，默认也只使用第一帧，其余真实图像不会用于重建。

因此，生成新视角的深度与“对观测视频逐帧估深度”不是同一个已实现功能。官方展示了后者；现有接口和训练样本没有覆盖它。把目标相机设回参考相机也不能保证重建，因为生成的 RGB 没有被固定为观测图像。

修正方向：在任务与模态掩码中支持“RGB 已知、只生成深度”，训练相应样本，推理保留观测 RGB。然后另行保留“给定目标相机，联合生成 RGB／深度”的任务。

## F2：高影响复现差异——固定四通道目标与像素 Transformer

位置：`open_atlas/model.py:27`、`:31`、`:36`、`:45`、`:60`。

当前上下文固定为 RGB，目标固定为拼接的 RGB＋深度，两个卷积 patch 编码器后使用标准 `TransformerEncoderLayer`。它可以做逐帧自回归，但没有按模态组织的独立图像／深度序列元素、可选深度上下文或任务切换，也没有文本分支。

Atlas 公开描述采用 latent diffusion 和多模态序列元素生成。当前直接处理像素，没有 VAE／潜变量编码解码；不能将这称为仅缩小网络宽度和层数。

与参考 DiT 的主要实验配置相比，当前也缺少逐块 adaLN-Zero 调制及相应初始化，只在输入 token 上加扩散时间嵌入。DiT 论文比较过多种条件注入方式，不能说“无 adaLN 就不是任何 Diffusion Transformer”；准确结论是：当前未实现其主实验骨干。Atlas 是否使用完全相同的 adaLN-Zero 并未公开，不能作强制要求。

修正方向：明确保留哪些 Atlas 公开机制；如目标是架构复现，应保留模态／任务结构和潜空间建模，再缩小尺寸。RGB 输入不应意味着删除一切可选或预测得到的深度上下文。

## F3：中高影响泛化风险——相机没有以参考帧规范化

位置：`open_atlas/data.py:38`、`open_atlas/geometry.py:33`。

直接用场景世界坐标的 `c2w` 计算 Plücker 射线。同一视频、同一相对相机运动，仅改变世界原点，射线矩就会变，网络预测也可能变。整场景网格居中／缩放不能替代按参考相机定义坐标系。

CAT3D 第 3.1 节明确用第一参考相机的相对坐标以获得刚体坐标变换不变性；CameraCtrl 官方实现也提供相对位姿路径。当前并未实现这种处理。未训练小网络探针中，对所有相机整体平移 `[2,-1,0.5]` 后，输出速度最大变化约 0.39036；该数值只证明架构没有保证此不变性，不是训练后误差或泛化降幅。

修正方向：统一用 `inverse(T_world_from_reference) @ T_world_from_camera` 编码条件，并在导出点云时保留回到场景世界坐标的变换。相对相机与尺度约定必须在训练和推理一致。

## F4：时空能力缺口——没有时间顺序或物理时刻

位置：`open_atlas/model.py:30`、`:49`、`:51`，`open_atlas/data.py:78`。

不同上下文帧使用同一套图像位置编码、同一模态标记和相同的干净时间嵌入；数据加载器不传入 `timestamp` 或帧序号。这里的 `time_embedding` 是扩散时间，不是物理时间。交换历史帧及其相机，目标输出的最大差异仅为 `3.58e-7`，即浮点精度内一致。

这对静态场景的无序多视图上下文可以是合理设计，但它没有编码带方向的运动历史，不能凭这种训练声称已支持动态视频、物理演化或任意速度的时空模拟。现有数据本身也只有静态场景和相机运动。

修正方向：如果目标包括动态任务，需要独立的物理时间／时序标记与动态数据；不要把扩散时间当作视频时间。静态新视图任务可保留无序参考集合。

## F5：训练策略差异——并未实现 Diffusion Forcing

位置：`open_atlas/model.py:69`、`:74`、`open_atlas/data.py:82`、`open_atlas/sample.py:70`。

训练每次只对一个 RGBD 目标加噪，上下文始终为干净真值 RGB；推理上下文逐渐由生成 RGB 构成。这是单目标条件流与 teacher forcing，存在训练、滚动生成之间的上下文分布差异。Diffusion Forcing 的独立逐 token 噪声等级并未实现。

这不是 rectified-flow 公式错误，也不能据此断言偏离了某个未公开的 Atlas 训练细节。但文档中的“参考 Diffusion Forcing”不能等同于已经实现该方法。若以长序列为目标，应研究带噪上下文训练，并单独评估自由滚动，不能只看真值上下文的验证流损失。

## F6：深度质量与几何完整性缺少证据

位置：`open_atlas/model.py:76`、`open_atlas/train.py:60`、`open_atlas/sample.py:22`、`:73`。

当前联合流损失按 RGB 和有效深度像素计算，但训练日志没有独立深度误差、RGB 指标或跨视图一致性评测。写出有限深度只验证接口。无效深度像素不受深度损失监督，推理也不输出有效性／置信度；点云导出只保留有限正深度，不能保证点来自可信几何。零值“编码通道”解码为约 2.3166，而非无效深度，不能靠输出通道接近 0 判定无效。

没有显式几何一致性损失或重投影检查，不代表漏掉了 Atlas 某个已公开损失——官方未披露此细节。可确认的是本项目还没有证据支持跨视图几何准确性；简单拼接反投影点云也不等于完成三维重建或三维高斯生成。

修正方向：独立记录深度 AbsRel／RMSE、RGB 质量和跨视图重投影误差，注明归一化单位与评测掩码，并为点云融合加入有效性处理。深度应区分预测、实测与未知区域。

## 已确认正确的部分与验证边界

- Rectified Flow：手工计算 `x_t=(1-t)*noise+t*target` 与速度目标 `target-noise`，与代码损失的差为 0；从 0 到 1 的 Euler 更新方向一致。
- 相机射线：用旋转处理方向，平移通过射线矩进入；与 CameraCtrl 官方代码的数学构造一致。`[d,m]` 与 `[m,d]` 是固定通道排列的差别，从零训练时不是错误。
- 相机 Z 深度反投影使用未单位化的 `K^-1 p`，与深度约定一致；现有 Blender 平面测试核对了 Z 深度、颜色及坐标转换。
- 23 项自动化测试通过，包括无真值深度推理、无未来目标图像依赖。这些测试不等价于生成质量或论文指标复现。
- 结构探针在未训练小模型上执行，完整数值与范围声明见 [atlas-code-audit-probes.json](atlas-code-audit-probes.json)。

优先次序：先统一生成与重建任务的模态定义、相对相机坐标及独立深度评测，再决定潜空间骨干和时空训练的范围。继续延长当前单场景训练不会自动补上这些能力。

## 6000 步模型的独立测试场景结果

已完成训练并加载实际 `last.pt`，在 apartment_2 的六类轨迹上自由滚动生成共 138 帧。每段只提供首帧 RGB 与已知相机，后续图像与深度完全生成；生成结束后才读取目标标注评分。分辨率 32×32，Euler 20 步，采样种子 0。

| 指标 | 实测值 |
| --- | ---: |
| 生成 RGB 的全像素 PSNR | 11.03 dB |
| 重复首帧 RGB 基线的 PSNR | 17.00 dB |
| 有效目标深度上的 AbsRel | 0.4612 |
| 深度 RMSE（归一化场景单位） | 0.7288 |

PSNR 使用 RGB [0,1] 范围的全像素平方误差汇总后计算；深度只在真值大于 0、有限且不超过 10 的像素上评测，不进行尺度对齐。AbsRel 不是米制距离。六条轨迹来自同一个测试场景，不能当成六个独立场景。

该设置下，生成 RGB 的 PSNR 低于直接重复首帧，且深度误差明显；说明当前模型未达到可用的新视角／几何质量。单场景小模型、有限训练、轨迹分布和上述结构缺口均可能影响结果，此测试不能单独证明某项架构差异是原因，也不构成 Atlas 官方基准对比。详细协议与逐轨迹数值见 [atlas-code-audit-evaluation.json](atlas-code-audit-evaluation.json)。
